VIDEOJEV / ARCHITECTURE

VideoJev: 생성 대신 시간·선택지 판정

한 줄 요약: 영상과 질문을 처리한 뒤, 시간 후보 또는 제시된 답변 후보를 공유 cosine head로 점수화한다. 영상 이해 연구지만 임의의 대화 답변 생성·오디오 이해·도구 조작까지 자동 제공하는 것은 아니다.

논문 아이디어

두 프레임으로 이루어진 temporal group을 시간 셀로 보고, 질문의 사건과 관련된 셀을 판정한다. 추론은 threshold-adjusted logits에 maximum-sum decoding을 적용해 비어 있지 않은 연속 구간을 고른다. 선택형 QA는 사용자가 준 옵션 안에서 답을 고른다.

공개 구현에서 확인한 계약

  • predict_video는 영상 준비·vision encode 후 predict_features로 이어진다.
  • 질문은 id/task/query, 선택형이면 options를 사용한다. 우리 검증기는 질문 목록만 검사하며 영상 파일을 받거나 열지 않는다.
  • Joint 묶음의 뒤 질문은 앞 질문 텍스트를 볼 수 있다. 질문 독립성이 필요한 평가에서는 이 조건을 통제한다.
구간 출력 ≠ 사건 존재threshold-adjusted logits가 전부 음수여도 raw decoder는 가장 강한 단일 셀을 고르며 후처리로 구간이 조정될 수 있다. 따라서 사건이 없는 영상에도 구간이 나올 수 있다. 구간만으로 존재를 인증하거나 여러 분리 사건의 탐지 결과로 확장하지 않는다.

근거: 논문 §2·관련 부록, 공개 HF processing/modeling/temporal 경로. 상세 파일·함수·행 번호는 VideoJev reference.

VIDEOJEV / CRITICAL ANALYSIS

VideoJev: 캐시를 구분해야 도입을 판단한다

항목논문·설명과 실제 코드의 관계
영상 특징 재사용공개 HF API에서 vision features를 재사용한다. 매 질문 묶음의 언어 forward까지 생략하는 뜻은 아니다.
Prefix cache공개 HF forward는 use_cache=False. 별도 연구 코드에는 실제 prefix-cache 경로가 있다. 두 경로를 같은 기능으로 설명하지 않는다.
평가 스크립트 명칭evaluate_cached_contexts.py는 Joint 경로를 호출하지만 report label에는 private cache forks가 언급된다. 파일명·보고 문자열보다 call graph를 확인한다.
학습 재현공개 custom 4B 설정의 192K/ZeRO-3와 논문 경로의 144K/ZeRO-2가 다르다. 설정 차이는 곧 결과 오류라는 뜻은 아니지만 동일 재현의 증거도 아니다.

어디에 유용한가 — 권장 활용 설계

긴 영상에서 사람이 검토할 사건 후보 구간을 좁히거나, 동일 영상에 대한 정해진 질문 묶음을 평가하는 보조 도구가 후보가 된다. 예를 들어 “물체가 프레임에 들어오는 구간”을 찾고, 실제 존재 여부와 최종 구간을 사람이 확인하는 방식이다.

실행 전 평가할 것

  • 사건 없음·짧은 사건·작은 물체·반복 사건·모호한 선택지를 포함한다.
  • Temporal IoU와 선택형 정확도뿐 아니라 false positive·검토율을 기록한다.
  • 프레임 sampling·decode·vision encode·언어 forward·후처리의 지연을 구분한다.
  • 옵션 순서·질문 순서·Joint와 단독 호출·실제 cache 경로를 따로 비교한다.
우리 workflow에 반영한 것video-grounding·video-choice 후보 계획과 질문 계약 검사. 아직 GPU 추론 adapter나 사건 부재 검증기는 아니다. 논문의 speedup을 다운로드·영상 decode까지 포함한 로컬 end-to-end 성능으로 옮겨 쓰지 않는다.

읽은 범위: 본문 §§1–6, 표·참고문헌, Appendix A/B. 시각 확인 범위와 미재현 지표는 상세 reference에 별도 표시. [R9]

MJEV-SPATIAL / ARCHITECTURE

MJev-Spatial: 공간 판단을 후보 선택으로

한 줄 요약: 이미지·질문에서 공간 관계, 수치 또는 위치를 판단한다. 기존 attention의 Q/K 표현으로 후보를 점수화하고, 수치·좌표는 coarse-to-fine 단계로 좁혀 간다.

작업입력·출력의 해석
Choice공간 관계 등 주어진 옵션을 비교한다. 안정적인 option ID와 텍스트를 구분한다.
Scalarm·count·deg를 구분한다. 단위가 다른 MAE를 하나의 수치로 합치지 않는다.
Point공개 기본 경로는 단일 normalized_xy point. 원본 이미지의 정규화 좌표이며 화면·실세계 좌표와 자동 호환되지 않는다.

코드에서 확인한 흐름

CLI의 입력 정규화 → image processor → native Q/K scoring → scalar codebook 또는 point refinement → decode. 학습의 teacher-forced 단계와 추론에서 예측한 단계는 구분해야 한다. 앞 단계 오류가 후속 crop·후보 선택으로 전달될 수 있다.

정밀도 ≠ 정확도, 좌표 ≠ 권한세분화된 codebook은 출력 해상도를 높일 뿐 정확도를 보증하지 않는다. point를 반환해도 대상 존재·좌표 변환·DOM 매칭·클릭 승인·로봇 안전을 별도로 검증해야 한다.

본문 §§1–5·Appendix A–H와 실제 입력·Q/K·decode·학습 경로를 대조했다. 상세 reference.

MJEV-SPATIAL / RELEASE GATES

MJev-Spatial: 설계 채택과 실행 승격은 별개

확인한 문제정확한 범위·해석
Dependency 충돌선언된 inference/train extras의 transformers==5.17.0는 Hub >=1.5,<2를 요구하지만 저장소는 Hub <1을 요구한다. 모든 설치 방법이 실패한다고 일반화하지 않는다.
Checkpoint 저장documented train 경로가 output directory를 만들고 save 함수가 같은 경로를 다시 exist_ok=False로 생성한다.
공개 API exporttop-level JevSpatial export가 존재하지 않는 inference 모듈을 참조한다. 다른 직접 진입점과는 구분한다.
Checkpoint 대응공개 metadata와 논문 최종 학습 설정의 대응이 불명확하다. metadata만으로 가중치 오염이나 논문 결과의 부정을 단정할 수 없다.
평가 범위공개 기본 evaluator의 accuracy·MAE·point distance는 논문의 mask·multi-point·macro benchmark 전체 harness가 아니다.

도입 순서 — 권장 설계

  1. 고정 revision에서 의존성·진입점·저장 lifecycle을 별도 scope로 수정·검증한다.
  2. 체크포인트의 학습·평가 데이터 계보와 코드·논문 대응을 확인한다.
  3. 라이선스·backbone 조건·환경·메모리를 기록하고 작은 실제 추론 smoke를 실행한다.
  4. 독립 holdout으로 단위별 수치 오차, point 위치 오차, 대상 부재·가림·복잡한 장면을 평가한다.
현재 채택 수준공간 관계·수치·단일 point의 설계 reference와 오프라인 입력 계약만 제공한다. BLOCKED_SOURCE_ISSUES를 유지하며 실제 backend는 켜지 않는다. 도구가 유효한 요청이라고 판정해도 이 차단 상태는 해제되지 않는다.

활용 후보는 이미지의 위치·관계를 사람이 재검토하는 보조 분석이다. 실시간 조작·정밀 측정·자동 클릭 등은 별도 교정과 권한 검증 없이 연결하지 않는다. [R10]

JEVA / DECISION ARCHITECTURE

Jeva: 후보 경쟁과 후보 부재를 분리한다

한 줄 요약: 요청과 옵션을 따로 인코딩하고, 고정된 option memory를 읽어 요청 상태를 갱신한다. “후보 중 무엇이 좋은가”와 “이 후보 집합에 답이 있는가”를 서로 다른 양으로 표현한다.

양의미
조건부 확률 q제시된 후보 안에서의 경쟁 분포. 공개 candidate_probabilities·conditional_probabilities는 이 값을 가리킨다.
Joint mass pp_i = (1 - p_null) × q_i. 후보 coverage를 반영한 질량이다. 조건부 q와 섞지 않는다.
Null적절한 답이 후보 집합에 없다는 결과. 일반적인 불확실성·정답률·검토 승인과 같지 않다.
Typed valueNoul은 positive option의 조건부 질량, Score는 명시한 values와 조건부 q로 계산한다. 보편적인 고정 점수 척도가 아니다.

실제 API 경계

우리 검증기는 raw predict의 state/question/decision_type/options/allow_null 형태를 제한적으로 검사한다. Score는 values, Noul은 positive_index를 명시한다. TypeSafe 요청 JSON이나 평가 label 파일을 그대로 받는 API가 아니다.

닫힌 집합과 열린 집합을 명시한다typed Noul/Score는 closed-set이지만 raw 경로의 허용 범위는 다르다. 우리 adapter 정책은 후보 두 개 이상, null은 Choice에만 허용한다. 이는 독립적인 안전한 subset이지 upstream 전체 계약을 바꾼 것이 아니다.

JEVA / CRITICAL ANALYSIS

Jeva: 아키텍처의 장점과 재현의 빈틈

왜 이 구조가 의미 있는가

옵션 표현을 요청과 분리하면 반복되는 후보 집합을 재사용할 수 있고, 후보 순서 변화에 대한 평가도 명시적으로 설계할 수 있다. coverage를 따로 두면 후보가 모두 부적절한 상황을 단순한 “가장 덜 나쁜 답”과 구분할 여지가 생긴다. 다만 이는 구조적 설계 의도이며 운영 품질·보정·캐시 이득의 실측 보장은 아니다.

대조 항목발견한 차이와 적용 규칙
후보 수raw 및 typed Choice/Score의 공통 inference validator는 singleton을 허용한다. 논문·evaluator의 최소 두 후보 조건과 구분하고 우리 검사에서는 두 개 이상을 요구한다.
Permutation 평가문서의 any-flip/all-order/TV와 공개 summary의 changed-variant agreement·maximum drift는 같은 지표가 아니다. 필요한 지표를 별도 계산한다.
학습공개 trainer는 논문의 auxiliary loss·단계별 curriculum·별도 optimizer parameter groups를 모두 재현하지 않는다.
Cache 표본본문·그림의 50과 부록의 46이 다르다. 원인이나 정답 denominator를 추정하지 않고 불일치를 기록한다.
배포 라이선스코드·가중치·backbone 조건을 각각 확인한다. 기본 download/export 경로만으로 모든 LICENSE·NOTICE가 보존된다고 가정하지 않는다.

권장 평가 시나리오

  • 정답 후보 있음·없음, 비슷한 오답 추가, 후보 순서 변경을 분리한다.
  • 안정적 option ID로 정렬한 뒤 확률 변화를 비교한다. 텍스트 중복을 임의 제거하지 않는다.
  • 같은 모델·tokenizer·옵션·설정에서 cache/no-cache 품질과 실제 지연을 비교한다.
  • null false accept/reject와 review 정책을 평가한다. null을 곧바로 승인·거절 명령으로 쓰지 않는다.
우리 workflow에 반영한 것text-choice·text-noul·text-score 계획과 입력 검증. 후보를 추천·분류하는 보조 설계로 사용하며 모델 호출·업무 라우팅·자동 권한 부여는 수행하지 않는다.

전체 본문·Appendix A.1–C.7과 typed/raw API·평가·학습 경로를 대조. 상세 reference. [R11]
